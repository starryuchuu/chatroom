# 端到端加密

v1.3.0 的桌面客户端在本机加密私聊和群聊正文，服务端只接收、保存和转发密文。单密码 OPAQUE 认证解锁随机端到端身份；消息路由继续使用原有已认证传输。传输会话密钥、服务端 RSA 私钥及数据库存储密钥本身不能解开新的端到端密文。账号迁移、改密及恢复步骤见[单密码指南](SINGLE_PASSWORD.md)。

当前 v1.3.3 保持 v1.3.0 起的协议、数据库结构和密钥格式，修复历史分页并更新依赖；已经升级为 OPAQUE 的账号无需再次迁移。建议客户端与服务端一并升级。

## 首次使用与身份核对

1. 先将所使用的 Python 或 Go 服务端升级至 v1.3.0，再使用新版客户端；缺少 `opaque_v1` 或 `e2ee_v1` 能力时停止连接。
2. 新账号注册和正常登录只输入一份统一密码。旧账号先选择“迁移旧账号…”，明确提供旧登录密码、原本机密钥口令和新统一密码；缺少已登记身份对应的原私钥时停止，不替换身份。
3. 新注册时在本机创建随机身份并登记公钥；已有账号登录时解锁或恢复原身份。联系人也需要建立端到端身份，之后才能收发新消息。密钥尚未准备好时会保留输入并停止发送，不会退回明文。
4. 在“加密与密钥…”查看自己的指纹，通过当面、电话等其他可信渠道，与联系人本人核对指纹，再标记为已核对。首次收到的有效身份会固定在本机；首次信任本身不能识别恶意服务端提供的替代公钥。
5. 首次向群聊发送，以及群成员或密钥变化时，需要明确确认接收人。收到群消息时也检查已批准的接收人范围。未批准或验证失败的内容不会作为可信明文显示。

v1.3.2 的“标记已核对”绑定窗口显示的指纹，保存时在密钥库锁内再次比较最新记录；其他窗口或进程已更换联系人密钥时停止旧确认，须刷新并重新核对，不能把未见过的新密钥直接标为可信。

联系人密钥改变会停止发送和验证，必须通过其他可信渠道重新核对。服务端不能自行替换已经登记的账号身份。群成员加入后，只能解密包含其密钥的新消息；移除成员后，之后的新消息不会再为其封装密钥。已经共享给旧成员的消息无法撤回其解密能力。

更换已固定的联系人密钥或批准群成员变化后，旧密钥和旧名单只用于验证**本机此前已经记录过的原始消息**，还必须匹配已保存的封装摘要及服务器编号。尚未记录的旧消息会被阻止，即使服务端声称它来自历史；这能防止已移除成员或已泄露旧密钥伪造新的“历史”。完整密钥备份包含这些观察记录。若群成员确实重新加入，选中该群后在密钥窗口点击“确认当前群接收人…”重新核对当前名单；这不会发送聊天正文。确认后可重新登录以重新读取先前被阻止的消息。

## 本机密钥与备份

密钥文件位于客户端配置目录的 `e2ee/` 子目录，按服务器和账号隔离。v2 文件用 OPAQUE 导出密钥派生的包装密钥加密身份，再由稳定身份派生另一层密钥保护完整本机信任数据；AES-GCM 认证绑定账号、服务器身份和格式上下文。客户端只上传加密的身份备份，不上传明文私钥、联系人信任、群批准或重放记录。

- 正常登录使用统一密码解锁，导出密钥仅在客户端取得。新设备可恢复同一身份，但联系人与群接收人需重新核对。
- “加密与密钥…”中的“导出加密密钥备份…”保存完整离线备份，仍由导出时的统一密码经 Argon2id 与 AES-GCM 保护；直接复制 v2 文件不是可凭密码独立解锁的备份。
- 登录页“恢复密钥…”支持原 v1 完整备份，恢复需要导出时的密码或旧本机口令。只能恢复同一账号；服务器地址或端口变化需要明确确认。
- 迁移已在服务端提交但本机仍为 v1 时，点击“解锁旧密钥…”输入原本机口令，再用新统一密码正常登录，保留原本机信任，不重复迁移账号。
- “修改账号密码…”更新服务器认证与本机包装，不改变身份指纹。本机已有的 v2 信任记录可在另一设备改密后通过同一身份验证并保留，云备份不能覆盖或回滚信任。
- 改密不会改变已导出的文件，其仍需导出时的密码；请重新导出。恢复较旧的完整离线备份后，重新核对期间发生的联系人密钥及群成员变化。
- 服务端登记公钥与解锁的私钥不符，或本机数据无法验证时停止，不生成或覆盖身份。
- 离线备份导出必须使用独立文件；本机库自身路径及其符号链接、硬链接别名均拒绝，避免备份覆盖运行中的密钥库。

**统一密码及所有可用密钥、离线备份与恢复凭据全部丢失后，没有服务端恢复账号或历史端到端消息的保证。** 云备份用于正确认证后恢复身份，不是忘记密码的绕过通道。

## 消息格式与两端兼容

服务端通过 `e2ee_v1` 和 `opaque_v1` 声明加密与单密码支持。v1.3.0 桌面客户端要求两项能力，缺少时拒绝连接并提示升级。尚未迁移账号保留显式旧客户端认证；升级为 OPAQUE 后拒绝该账号的旧认证。已有账号在登记端到端身份后，服务端拒绝该账号的明文发送，也拒绝向已登记身份的接收人发送明文。

每条消息使用独立随机的 256 位内容密钥和 AES-GCM nonce。客户端用临时 X25519 密钥，与每位接收人的静态交换公钥生成共享秘密，再用 HKDF-SHA256 派生独立的封装密钥。私聊包含发送人和接收人的密钥副本；群聊为当时全部已确认成员逐一封装，因此离线消息、发送者历史和分页补取都不依赖服务端掌握内容密钥。

Ed25519 签名绑定版本、随机消息 UUID、发送者、会话类型与目标、发送者公钥、接收人及其指纹、临时交换公钥、nonce、密文和密钥封装。正文 GCM 的附加认证数据绑定消息头；密钥封装同时绑定消息头和接收人。签名输入采用排序键、紧凑分隔和 ASCII Unicode 转义的 JSON，Python 与 Go 通过同一互操作向量验证。

数据库通过已有 `messages.e2ee` 标志区分密文封装和旧消息，避免把恰巧长得像 JSON 的旧正文误判成端到端密文。两个服务端以相同方式保存公钥与密文。实时投递、登录历史、向前补取及向后分页均保持原密文封装。服务端在保存前检查身份、签名、当前接收人集合及帧长度；群成员检查与发送在同一组操作锁内进行。

旧历史不会追溯变成端到端加密，界面会明确显示“旧消息 · 非端到端加密”。从端到端与单密码功能引入以前的版本升级时，先备份数据库和存储密钥，再由新版服务端完成所需表和字段迁移，不再用旧服务端打开该库。从 v1.3.0 / v1.3.1 / v1.3.2 升到 v1.3.3 没有新的数据库结构迁移。

## 保护范围与限制

- 保护消息正文；账号、关系、群成员、路由、时间、大小和流量等元数据仍可由服务端观察。
- 不采用双棘轮协议，**不提供长期接收私钥后来泄露时的前向保密**。取得某接收人的私钥及历史密文，可能解开此前发给该身份的消息。临时发送密钥不能消除这一限制。
- 首次公钥信任需要独立渠道核对。恶意服务端仍可以丢弃、延迟、重排消息或拒绝服务；签名不提供服务可用性保证。
- 客户端保存最近 10,000 条已验证消息的签名 UUID 与服务器编号对应关系，拒绝把同一封装换成新编号后重复显示。该检查有保留范围，不代表无限期的全局消息排序或审计保证。
- 每条加密消息的 UTF-8 正文上限为 256 KiB，最多 256 位接收人；完整封装仍受 1 MiB 帧上限约束。
- v1.3.2 两服在创建群、邀请与接受邀请时共同检查 256 位实际成员上限（含群主），与消息接收人上限一致。邀请不预留名额，满员时可在容量释放后重试尚未过期的邀请。
- 解锁后的本机、截图、被恶意修改的客户端及接收人主动泄露正文不在加密所能保护的范围内。

消息加密使用 PyCryptodome、Argon2 CFFI、Go 标准密码库及固定版本的 Edwards25519 公钥校验依赖。单密码认证共用 `opaque-ke=4.0.1`（RFC 9807）WASM 核心，Python 使用 `wasmtime==50.0.1`，Go 使用 `wazero`。上游历史审计不代表该版本、本项目包装或集成经过独立审计；依赖、构建和恢复边界见[单密码指南](SINGLE_PASSWORD.md)。
